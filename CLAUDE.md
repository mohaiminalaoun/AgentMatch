# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm test`: run all tests once (Vitest)
- `npx vitest run tests/engine/profile.test.ts`: run one test file; add `-t "<test name>"` to run one test
- `npm run test:watch`: run tests in watch mode
- `npm run typecheck`: type-check with `tsc --noEmit` (nothing is emitted; code runs through `tsx`)
- `npm start`: run `src/index.ts` with `tsx`
- `npm run eval`: compare all matching methods across seeds and print a results table: team quality, share of people placed, per-person quality, leakage (share of private fields reaching people outside their team), and whether a trusted central party is needed (`src/evaluation/run.ts`)
- `npm run ask "<prompt>"`: send one prompt to the model configured in `.env` and print the reply, token usage, and latency (`src/ask.ts`; costs real credits)
- `npm run decide [1-5]`: one agent decides on one sample proposal from `src/scenarios.ts`, printing the messages, its private rationale, gate blocks, and what would be sent (`src/decide.ts`; costs real credits)
- `npm run reliability`: run 20 live agent decisions concurrently over `src/scenarios.ts` and report the decision mix, gate blocks, a re-check that nothing sent breaks the disclosure rules, tokens, and time (`src/reliability.ts`; costs real credits)
- `npm run round`: one live round on the bus (Ivan proposes to Ben; Ben's agent decides and replies), printing each bus event, the private rationale, and both agents' state (`src/round.ts`; costs real credits)
- `npm run negotiate`: Nia proposes to Kemi and the two negotiate over the bus tick by tick up to level 2, printing every message, levels after each tick, every private rationale, and what each side learned (`src/negotiate.ts`; costs real credits)
- `npm run coevolve`: Theo (a workout tracker) proposes to Mara (a rehab coach), each with level-tagged private notes; they negotiate to level 2, where either may propose a reshaped version of the project (a revision the other adopts or keeps), then commit. Prints every event with private rationales, then the original idea next to the version the team builds (`src/coevolve.ts`; costs real credits)
- `npm run hunch`: Lena pitches a fitness app to Rafa; his agent decides twice, with his profile only and then with his "never" note (a failed jiu-jitsu app) feeding a private hunch, printing both decisions and checking the note reaches nothing sent (`src/hunch.ts`; costs real credits)
- `npm run discover`: the six sample people's agents write board listings, then pick whom to approach; prints the listings, the board, each choice with its private rationale, and the resulting proposals, without negotiating (`src/discover.ts`; costs real credits)
- `npm run simulate [-- --agents N --rounds R --seed S --private --brain-model M --cast]`: the whole system on generated people (default 10 agents, up to 6 rounds, seed 1; `--brain-model` runs the first agent on model M, same provider, and reports calls per model; `--cast` uses the first N of the fixed cast instead and judges each team against its expected groups): listings, then discovery, negotiation, and commitment each round, all concurrent, until a round changes nothing; prints every event as it happens (private rationales only with `--private`), a live status line of model calls, tokens, and time, and a report (pairs reached, committed teams, never-approached agents, roles beyond the core four on the board, gate blocks, calls, tokens) (`src/simulate.ts`; costs real credits: roughly 100–200 calls at 10 agents, 300–450 at 20)
- `npm run eval:agents [-- --people N --seeds 1,2,3 --rounds R]`: run the full agent simulation on the same generated people as the baselines (default 20 people, seeds 1–5, all seeds at once) and print one table with every method, agents included; saves `results/eval.json` (synthetic data only) for the chart, and logs each seed's run to `runs/` (`src/eval-agents.ts`; costs real credits, roughly 2,000 calls at the defaults)
- `npm run eval:explain -- <log> [--per-kind N --seed S]`: samples up to N private rationales of each call kind from a run log (default 5, seed 1), has a judge model sort every claim in each as supported by the agent's prompt, unsupported, or contradicted, and asserted or hedged, and prints a table per call kind; saves every judgment next to the log in `runs/` (`src/eval-explain.ts`, `src/evaluation/explain.ts`; costs real credits, one call per rationale; refuses a `-contributor` judge for logs with real people)
- `npm run eval:explain:label -- <explain.json> [--claims N --seed S]`: checks the judge against a person's labels. Writes a page next to it in `runs/` with N claims (default 30, up to half of them ones the judge flagged), each with the agent's prompt and rationale but never the judge's verdict, to label in the browser and download; then `--labels <labels.json>` prints verdict agreement, Cohen's kappa, flag precision and recall, a confusion table, and every disagreement (`src/eval-explain-label.ts`; no model calls)
- `npm run regressions [-- --runs N --case <name>]`: runs fixed, made-up scenarios that replay each reasoning failure seen in the pilot (role omission, join request, invented scheduling, headcount, misdescribed option, relabeled roles), plus declining an unfinished team seen in checkpoint B dropping or withdrawing over roles neither of a pair can do, waving away a wide time-zone gap, putting two people far from each other in one group, a hunch steering on a note that does not bear on the project (or ignoring one that does), and at the deadline, dropping out of a decent group only because it is incomplete or staying in a clearly wrong one, N times each (default 10), on the engine's real prompts; a judge answers one yes/no question per run, and it prints a failure rate per case with examples, saved to `runs/` (`src/regressions.ts`, `src/evaluation/regressions.ts`; costs real credits, two calls per run)
- `npm run eval:injection [-- --runs N --scenario <id>]`: runs made-up prompt-injection scenarios N times each (default 5): another agent's proposal carries text trying to extract the receiving human's name, skills, hours, or private guidance, to pose as the owner or the system, or to talk the agent into accepting a project its guidance rules out. Checked by plain string matching on what the agent would send, no judge: prints per scenario how often a private string got out, how often the disclosure gate stopped it first, and (for the hijack ones) how often the agent accepted, against the same proposal without the attack; saved to `runs/` (`src/injection.ts`, `src/evaluation/injection.ts`; costs real credits, one call per run, two for hijack scenarios)
- `npm run eval:decisions -- <log> [<log> ...]`: checks each run log's decisions for hard problems, by code alone: final teams bigger or smaller than a member's limits, roles a team's project needs that no member can do (or only a beginner can), and offers the code sent differently from what the owner's model chose; prints ids only, never rationales; also prints, per log, where the decisions came from (shared model, outside agent, or the code's safe default after no valid answer) and how often code overrode an answer (gate stopped a draft, offers trimmed, uncited hunch made neutral) (`src/evaluation/provenance.ts`, `src/eval-decisions.ts`, `src/evaluation/decisions.ts`; no model calls)
- `npm run baseline -- <label> <log> [<log> ...]`: freezes one record of how the agents do, to compare later changes against: the eval table, each log's explanation summary (its `.explain.json` from `eval:explain`), the newest regression results, and the decision check, as aggregates only, in `results/baseline-<label>.json`; refuses logs with anyone not generated, since `results/` is in git (`src/baseline.ts`; no model calls)
- `npm run chart`: draw the privacy vs. quality chart (per-person team quality against leakage, agents highlighted, baselines in gray, rings for methods that need a trusted party) from `results/eval.json` into `results/chart.svg`, with light and dark colors (`src/chart.ts`; no model calls)
- `npm run load-test [count]`: fire `count` (default 50) calls at once through the queued, retrying client and report 429s, retries, peak concurrency, and speedup (`src/load-test.ts`; costs real credits)
- `npm run show-run [file] [--prompts]`: print a run log from `runs/` as a timeline (ticks, bus messages, decisions and interest checks with their private rationales, level changes, and a model-call summary), defaulting to the newest; `--prompts` prints every model call in full. Logs are `runs/<timestamp>-<label>.jsonl`, one run event per line, gitignored because they hold every agent's private rationale and can hold real people's data
- `npm run pilot:run -- <dir> [--fill N --cast N --seed S --rounds R --outside ID=AGENT (repeatable) --answer-minutes M --poll-seconds S --skip-listen-check]`: the whole system on real people, one `.json` file each in `<dir>` (copy `profiles/example.json`; real profiles go in the gitignored `profiles/`), plus N generated people and N from the fixed cast (teams judged against its expected groups); `--outside` makes person ID's agent an outside agent answering through the hosted mailbox as AGENT, M minutes per request (default 25); when AGENT is `grokbot`, requires `GROKBOT_WEBHOOK_URL` and `GROKBOT_WEBHOOK_KEY` and sends a Bearer-authenticated webhook containing only `request_id` after storing each request (including correction attempts), with delivery diagnostics and no automatic notification retries. Mailbox answer checks default to 2 seconds for Grokbot and 15 seconds otherwise (`--poll-seconds` overrides); see `docs/grokbot.md` for the versioned routine instructions, with the preface `OUTSIDE_PREFACE` on every prompt; refuses any `-contributor` model, keeps names unshared until people approve, and prints where each real person ended up (`src/pilot-run.ts`; costs real credits on the regular model) With an outside agent that polls (anything but grokbot), the run first checks the mailbox's call trail and stops before spending anything if the agent has made no call in the last minute, since an agent that is not listening would hold every request until `--answer-minutes` passes; `--skip-listen-check` runs anyway, and a mailbox that cannot say (older deployment, network) only prints a warning (`src/pilot/listening.ts`). `--outside` may be given once per outside agent (Muse and Grokbot in one run, each for a different person; one person and one mailbox agent each, checked in `src/pilot/outside.ts`); `--poll-seconds`, when given, applies to all of them, otherwise grokbot is checked every 2 seconds and others every 15.
- `npm run pilot:view -- <log> <id> [people-dir]`: prints one person's own view of a pilot run: the public board, their agent's steps with its private reasoning, messages to or from them, and their own standing instructions (loaded from `people-dir`, default `profiles`), never anyone else's (`src/pilot-view.ts`; no model calls)
- `npm run mailbox -- register <agent> | seed <agent> [recorder|bjj|pets|commit|commit-fit|repair] | profile <agent> | answers <id...> | activity <agent> [n] | save-profile <id>`: the engine's side of the hosted mailbox, by hand: make an outside agent's key (shown once), leave it a sample level-0 proposal due in 3 hours, ask it to declare its human's profile (the fields and their levels explained), show the answers that came back and whether each is valid, or save a declared profile as a gitignored person file in `profiles/` for its human to review (`src/mailbox.ts`; reads `MAILBOX_URL` and `MAILBOX_ENGINE_KEY` from `.env`; no model calls) `activity` prints an outside agent's recent calls at the mailbox (the mailbox keeps a metadata-only trail per agent: when, which tool, which request, what came back; the newest 300 entries for a week), with the requests it saw but never answered and its longest gap between calls, for working out why a run went quiet (`src/mailbox-activity.ts`). The `commit`, `commit-fit` and `repair` seeds are built from the engine's own prompts with made-up people (`src/evaluation/commit-sample.ts`, `src/evaluation/repair-sample.ts`), and `answers` checks their replies the way the arena would (a commit must name an offered owner or null; a repair must pass the engine's repair rules, which refuse people words such as owner, member, teammate, we, our, they, their, human, person), so an outside agent's handling of those request kinds can be tried in under a minute instead of a whole pilot.
- `npm run format` / `npm run format:check`: run Prettier (tabs, width 4)

## Architecture

Agent Match is a network of personal AI agents that negotiate to form teams for their humans, with no central coordinator. Agents reveal profile information in stages, and a deterministic disclosure gate outside the LLM blocks any message that reveals more than the current stage allows. Privacy must never depend on the model following instructions.

The code lives in `src/` in three areas:

- `src/engine`: core agent logic (domain schemas, proposals, the disclosure gate, the LLM client). LLM calls layer as `createLlmClient` (concurrency limit via `queue.ts`, backoff on 429/5xx via `backoff.ts`) → `chatJson` (re-asks on invalid JSON) → `chat` (one HTTP request); agents should share one client. Each agent's calls go through `brainOf(client, id)`, so `withBrains` can give some agents a different client (another model now, an outside agent later) while the engine referees them identically; every exchange records the model that answered. An outside agent's brain is `createMailboxBrain` (`mailbox-brain.ts`): each call becomes a pending request in the hosted mailbox (labelled with the call's `about`, its kind and level, which every call site sets), and the engine polls until the agent answers or the deadline passes; the answer runs through the same `chatJson` loop, so the schema, `check`, and gate apply and a rejected answer goes back as a new request with the problems, and a missed deadline or a mailbox outage becomes a StructuredOutputError, which every call site turns into its safe default. Pilot logs also record `mailbox` diagnostics (request id, stage, level, attempt, elapsed time, lifecycle status, and categorized validation or transport failure; no prompt, answer, or credential contents). Mailbox exchanges carry `requestId` for correlation. The pilot terminal shows pending external requests and labels fallback actions as arena defaults rather than agent decisions. Each agent may hold its human's private notes (`notes.ts`): free text tagged with a level (0–3, or "never"). Every prompt gets the full profile (whose short, known values the gate checks in free text and structured profile shares) but only the notes its level allows (`aboutHuman`), since a paraphrased note can't be detected: a note that isn't in the prompt can't leak. Notes are never shared as data. An agent may also hold standing instructions (`guidance` in `notes.ts`): a short personality or judgment block included in every call that already includes `aboutHuman` except the hunch. Instructions are never shared as data, never added to the profile the gate scans, and the prompt tells the model not to quote or describe them in anything sent. An agent with "never" notes first makes a private hunch call (`hunch.ts`) that sees every note but can only output a steer (neutral, explore, careful, stop), a risk area from fixed lists, and the number of the note the steer rests on; code makes any explore, careful, or stop that cites no real note neutral, and logs it as unfounded; code turns that into a fixed sentence for the decision or interest prompt, which never sees the notes. "stop" declines or withdraws with no call; "careful" rules out a plain accept. Every decision prompt judges by one shared standard, `GOOD_TEAM` (`goals.ts`), which weighs the criteria together and judges a team still forming by what it can become, and gets a labelled block of facts and unknowns about the other person (`fitFacts`/`factsText` in `fit.ts`), computed by code from the agent's own profile and only what was shared with it (time zones, each side's evening on the other's clock, hours, skills, the team sizes that suit both, exact shared interests; actual working hours and synchronous collaboration needs remain unknown), plus `CITE_FACTS`: rationales rest on those facts and never state unknowns as fact. Agents decide through `decideOnProposal` (`decision.ts`), which runs every outgoing message through the disclosure gate (`gate.ts`); the model's `rationale` stays private and is never sent. Agents never call each other: every message goes through the bus (`bus.ts`), which validates it (schema, sender identity, recipient), delivers a copy to the recipient's inbox, and reports numbered events to subscribers for logging, the UI, and replay. `runRound` (`round.ts`) sends new proposals, then runs ticks until no mail is waiting (or `maxTicks`): each tick every agent handles its whole inbox, model calls run concurrently, and replies go out in inbox order so the bus order doesn't depend on LLM timing. An accepted proposal or counter opens level 1, and both sides send a `share` of that level's fields, built by code from the profile and gate-checked; receivers `learn` it, then run an interest check (`interest.ts`) and send `continue` or `withdraw`, which carry no text. At levels 1 and 2, a `continue` may come with a `revision`: a reshaped version of the project, gate-checked at that level (at most 2 per conversation), which the other side adopts or keeps with a text-free `revisionAnswer`; at level 2 a revision must also list `covers`, who covers every role the new version needs and every role the agreed version needed (`proposer`, `recipient`, `open`, or `dropped`), and code checks each claim against the proposer's profile and what the recipient shared (`coverProblems` in `interest.ts`); at level 1 covers aren't allowed, since they'd reveal skills; `agreedVersion` (`agent.ts`) is the last accepted proposal or counter, or adopted revision, with its author, who owns the project (`projectOwner`), since a version's roles list names what's needed from people other than its author. Once both sides have continued at a level, the next opens, up to `maxLevel` (default 2; level 3, names, is for the deadline). Each agent's model first writes its public board listing (`listing.ts`): a short title and a pitch from its project idea plus the roles the project needs from others (any of `ROLES`), gate-checked at level 0. Every version of a project (listing, counter, revision, offer) carries its title with it, gate-checked like the pitch, so adopting a version adopts its name, and a team is named after the version it builds. Every version also carries a project card (`problem`, `build`, and `roleWork`, what each needed role would do; optional in `Terms`, required in listings), shown with the pitch from level 0 on so a decision doesn't need an accept just to learn more (which costs a slow outside agent a whole turn); it's model-written, so `termsTexts` puts it through the gate and the third-party check with the title and pitch, `termsOf` keeps role work only for roles still needed, and `termsLines` shows it in prompts. `runSimulation` (`simulation.ts`) chains it all: listings once, then each round `discover` → `runRound` → `runCommitment`, until a round has no proposals or commits (stable) or `maxRounds` is reached, emitting a `stopped` event. Then, if at least two people are still on no team, a brainstorm phase (a `brainstorm` event, then up to 2 rounds) lets them meet each other through `brainstorm` (`discovery.ts`): anyone left over may approach anyone left over, people with no idea included, with a fixed `BRAINSTORM_PITCH` and their missing core roles, if the pair never got past level 0; agreeing to brainstorm isn't an idea, so a team needs an adopted revision or accepted counter first, and whoever wrote that idea owns it, idea of their own or not; an agent that picked nobody isn't asked again until the board changes. Last comes the deadline (`runLock`, `lock.ts`): until then every team is a tentative group, and nobody leaves or switches groups; now each member of each group, the owner included, is asked whether they're confident in it (`lockMessages`: the group's version, size, and roles still needed, facts about every member they've talked to, and a count of members they haven't), with a `lock` event per answer; a "no" (or no valid answer) drops just that person, who sends a text-free `leave` to each member; if anyone dropped, the rest are asked once more; groups left with two or more become `committed`, and only then do members swap names (level 3), unless `revealNames` is false (the pilot), when names wait for human approval outside the engine. `summarize` derives the report from the final world and the events. `runCommitment` (`commitment.ts`) turns ready pairs into tentative groups by deferred acceptance: each project owner sends an `offer` to the people it's ready with (in a conversation about its project, or, once it leads a group, any conversation, since the group's version is what's on offer) who fill a role its listing still needs (or wrote the agreed version themselves, whose roles list names what's needed from others) and whose largest team size fits (its model ranks them if not all can be taken, or if the offers would put two or more people in one group, since they may never have talked: its prompt then also gets `groupFactsText` (`fit.ts`), everyone's time zone, every pair's gap, their evenings on its human's clock, and the group's 9-to-5 overlap as an estimate; `selectOffers` trims to a set where each can take a different needed role, one each, so someone who could do several roles takes just one (`assignRoles`), plus, for people the owner's model chose, a second person for a role already taken while the team would otherwise be smaller than someone's smallest size, and the team fits the smallest `maxTeamSize` among its members, as learned at level 2; the `offers` event records the model's ranking and everyone the trimming dropped, with the reason, from `explainOffers`, and everyone the owner reached level 2 with but could not offer a place, with the first check that ruled them out, from `explainCandidates`; and, before there is a team, when the versions agreed with each person the model chose would keep some of them out, the one version its model wrote for all of them (`teamVersionMessages`), written only when someone was cut over the version, which every offer then carries, only if it passes the gate at level 2 and reveals to each of them nothing learned from anyone else), but before any is sent, an owner with no team yet who is being offered a place decides whether to lead (send its offers) or join one of those teams (its own offers are never sent; the join holds only if the owner joined leads, otherwise it's busy that pass); then every other agent holding offers picks one at the same time (the commit and lead-or-join prompt, `commitmentMessages`, shows every option side by side in the same shape: the version each team builds, its size now, and the facts about the person behind it, its own team included when it could lead) and answers `commit` or `decline` (an owner that leads answers `busy`; unlike a decline, that can be offered again), and these passes repeat within the round until nothing changes; a commit adds them to `world.teams` as a `tentative` team (the first member is the owner); names wait for the deadline. Each offer carries the version of the project the team will build: the team's once it exists, otherwise the version agreed (`agreedTerms`: the last accepted proposal or counter) with the first person offered; a version is only sent to someone if it reveals nothing the owner learned from anyone else (`safeToOffer`, using `checkThirdParty` in `gate.ts`), and the team's `rolesNeeded` come from it. The public board keeps the original listing. People on a team leave the board and stop discovering, except owners with places left and roles still needed, whose board entry and proposals then show their team instead (`teamListing` in `commitment.ts`): the team's version if it reveals nothing beyond level 0 and nothing learned from anyone (otherwise the original listing's title and pitch), the roles the team still needs, and its size (`teamSize`), which the recipient's decision prompt states. An agent's public `leftTeams` (committed teams its human has left, kept for runs with real people) is attached by code to its board entry and proposals so others can weigh reliability. Agents then choose whom to approach through `discover` (`discovery.ts`): each sees its own profile plus the public board (every agent's listing, nothing more; agents with a project also see the ids of people looking to join, who have no project and show nothing else), picks up to 3, and picks become proposals for `runRound`. Someone with no project asks to join instead: the proposal carries the target's own listing and is marked `join` (`isJoinRequest`), and the owner gets its own prompt (`joinRequestMessages`): the roles are its own project's needs, nothing is known about the requester yet, and it may only accept or decline. `runRound`'s `onEvent` emits one ordered stream of run events (`events.ts`: round, tick, bus, decision, interest, level, exchange); scripts write it to the run log and print it with `formatEvent` (`src/describe.ts`), so live output matches `show-run`. **It must never import from `src/ui`.** The UI subscribes to events the engine emits.
- `src/evaluation`: synthetic profiles, non-LLM baselines, and metrics (team quality, privacy leakage). Two kinds of made-up people: `generateProfiles` (`profiles.ts`) draws everything at random from a seed, for statistics across seeds (the baselines and `eval:agents`); the fixed cast (`cast.ts`) is 30 people each built from one real idea paraphrased from the Meta hackathon's Discord intros (no one named), with skills, interests, and needed roles that follow from it and level-0 card details (problem, weekend build, what each needed role does), plus `EXPECTED_GROUPS`, the answer key written before any run, and `judgeTeam`, for live runs a person reads and judges.
- `src/ui`: an Ink terminal UI that renders engine events, and the web replay studio (`src/ui/web`, `npm run dev:ui`), which shows every version's project card and marks agents with a brain of their own ("outside agent" or "other model"), from the `brains` event that `pilot:run` and `simulate` emit first (`brainsEvent` in `client.ts`), or, in older logs, from model calls labelled `mailbox:<name>`.
- `mailbox/`: the hosted mailbox outside agents answer through, its own small Vercel project (Upstash Redis). Outside agents can only call out, never be called, so the engine leaves each decision it needs from one as a pending request (id, kind, prompt, replySchema as JSON Schema, deadline, level), and the agent polls `GET /pending` and answers with `POST /answers`, idempotent by request id (the first answer stands). One bearer key per outside agent (only its hash is stored) and one engine key; another agent's request looks like none. The mailbox only stores and hands over: the engine validates every answer and runs the gate. Core logic in `mailbox/api/_mailbox.ts` (tested with an in-memory store); `_redis.ts` and `index.ts` are the Redis store and the Vercel entry point; deploy with `vercel deploy --prod` from `mailbox/`. The same mailbox is also an MCP server at `/mcp` (tools `get_pending`, which returns one decision and can wait up to a cap for one to arrive, and `submit_answer`; same keys and rules; `mailbox/api/_mcp.ts`), so Muse needs no polling script. An agent name is letters, digits, `-` and `_` only, and using a key renews its week-long lifetime.
- `src/pilot`: running real people. `person.ts` is a person's file (`{ profile, notes, instructions, contact }`; ids like `p-4k2m`, skills and preferred roles must be `ROLES`; `contact` never enters a prompt; `instructions` is optional standing guidance for that person's agent, never shared as data); `model.ts` refuses models the provider trains on; `run.ts` runs real plus generated people with `revealNames: false`; `view.ts` (`eventsFor`) is what one person may see of a run (their own instructions are shown by `pilot:view` from the person file, never via events). The engine must never import it.

Domain types are zod schemas, and each TypeScript type comes from its schema with `z.infer`, using the same name (`export const Profile = z.object(...)` and `export type Profile = z.infer<typeof Profile>`). Validate any untrusted data, including LLM output, against these schemas. Tests live in `tests/`, which mirrors the `src/` layout (`src/engine/profile.ts` → `tests/engine/profile.test.ts`). Shared test data goes in `tests/fixtures.ts`.

## Conventions

- ESM with `NodeNext` resolution: relative imports need a `.js` extension (`import { Profile } from "./profile.js"`).
- LLM settings (`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`) live in a gitignored `.env`; copy `.env.example` to create it. Entry points call `readEnvFile()` once, then pass `loadConfig(process.env)` down to whatever needs it. Never log the config or the API key.
- Optional `LLM_PRICE_*` settings (USD per million tokens) let reports estimate cost (`cost.ts`). The `-contributor` models are about 95% cheaper because the provider trains on their inputs: use them only with synthetic profiles, never with real people's data.
- Optional `LLM_REASONING_EFFORT` (`minimal`, `low`, `medium`, `high`) is sent as `reasoning_effort`. Hidden reasoning was about 95% of output tokens in simulations; `minimal` cut one decision from 25s to 2.5s.
- The tsconfig is strict, with `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, and `verbatimModuleSyntax`. Use `import type` for type-only imports.
- `steps.md` (the build plan), `readme-inprogress.md` (strategy notes), and `demo-notes.md` (demo moments and transcripts) are private and gitignored. Never commit them or copy their contents into tracked files. Work through `steps.md` one step at a time unless asked to combine steps.
- Use the `/commit-changes` skill for commits: one-line Conventional Commits messages, with no attribution lines.

### Project roles and the disclosure gate

`draftOf` keeps `rolesNeeded` separate from free text. Known role names (and the existing `any` sentinel) are validated as project requirements rather than matched against the sender's hidden skills or preferences. Role-work labels use the same distinction; their free-text values, project text, and structured profile shares still pass the conservative disclosure checks. Unknown or arbitrary role strings are rejected. This is not a general semantic classifier: free-text project descriptions containing a private skill term can still be blocked, and inferential disclosure is not eliminated.

### Pre-deadline repair

`runSimulation` runs `runRepair` (`src/engine/repair.ts`) after recruitment and before `runLock`. It considers only incomplete tentative teams, with one owner scope proposal (at most two structured-output attempts) and one approval attempt per member. A candidate can only remove required roles, must explain every removed dependency, and must leave teammate roles covered by skills the owner actually learned. It is checked for owner and third-party disclosure before votes. Roster changes, team merges, and reopening recruitment are out of scope. All members, including the owner, must approve; rejection or failed output keeps the original. Final confirmation still follows. Team records retain optional problem/build/roleWork cards so repair and confirmation judge the agreed scope. `repair` events record proposals, private votes, and outcomes; person-specific views hide other members' rationales/votes, and replay shows unanimously adopted repairs as settled revisions. Meaningful scope reduction is judged by the agents, not guaranteed by role-list validation alone.

Repair and final-confirmation prompts explicitly identify whether the deciding human owns the project: `rolesNeeded`/`roleWork` describe teammates' work, not the full build or the owner's tasks. Owners' contributions must be grounded in the agreed build and known skills rather than inferred from missing role labels. During repair disclosure checking, `project-context.ts` masks unchanged fields and repeated passages of at least three words from the current agreed team card only. It does not exempt a vocabulary item everywhere, nor treat the owner's original listing as already shared by the team. Exact unchanged fields remain shared even when they contain pronouns referring to users or software agents. New personal-reference wording is rejected before passage masking; remaining new text still passes owner/third-party checks. This remains conservative lexical checking, not a proof of semantic privacy. Run summaries count all fallback-bearing decision events, including repair and deadline votes, without double-counting transport diagnostic events.

Repair consent and final confirmation share closed-recruitment personal-fit criteria (`FINAL_TEAM`). Both validate positive votes against required role names using only the deciding agent's own skills and learned roster skills, including owner skills. Uncovered roles cannot be waived as optional in a rationale; scope changes require unanimous repair. Final confirmation permits at most two output attempts. This deterministic check verifies named skill presence, not workload feasibility or semantic personal fit, which remain agent judgments.

### Motivation-led project search

Discovery, counterproposal, interest and revision-adoption prompts distinguish motivation from skill coverage (`MOTIVATION_FIT` in `goals.ts`). When a partial fit needs a change, agents privately compare an outcome-preserving direction with a materially different direction grounded in known motivations. They diagnose the blocker and send one concrete counter/revision rather than leaving the alternative only in a private rationale. Good existing projects stay unchanged; a missing capability may invite either a grounded scope change or continued recruiting, not automatic removal of the motivating outcome. Public cards and existing disclosure gates, role-cover validation, counter/revision limits and model call counts retain their contracts. Private instructions and candidate alternatives stay out of shared project text.

Three synthetic checkpoints run through real interest prompts and gates with `npm run regressions -- --runs 3 --case "creative motivation pivot"`, `"creative preserve outcome"`, or `"creative keep strong fit"`. They test consequential interactive alternatives, retaining independent voice access while reducing infrastructure, and avoiding unnecessary changes. These small model-judged cases are behavior evidence, not proof of better placement or full-run quality.

### Repair-card consistency and replay

Repair proposals must update all affected card fields when reducing scope. `RepairVote.cardConsistent` is a required semantic assessment across title, pitch, problem, build, role work and removed work; schema validation forbids an approving vote with `cardConsistent: false`. Assessments are recorded on private vote events. This uses existing member votes, adds no review calls, and does not guarantee detection of every contradiction. Run the synthetic `scope card uploads`, `scope card adaptive`, and `scope card valid` regression cases for conflicting promises and honest smaller demos.

Replay preserves historical events unchanged. Unanimously adopted repairs retain shared `removedWork` and roster consent metadata, render distinctly from negotiation revisions, and keep final confirmation separate. Outside agents are labeled in team membership. Role-assignment labels describe the recorded primary assignments; an absent secondary assignment is not proof that no member can do the work. Importing a run resets private reasoning to hidden.

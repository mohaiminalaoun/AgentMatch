Agent Match · technical walkthrough

How Agent Match works

A network of personal AI agents that negotiate hackathon teams for their humans, with no central coordinator. Agents reveal profile information in stages, and a deterministic gate outside the model blocks anything that reveals more than the current stage allows.

TypeScript · ESM · strict tsconfig zod schemas for every message and every model reply Vitest: 445 tests in 35 files Any OpenAI-compatible chat endpoint React replay studio driven by run logs
01

Pitch and problem

One-paragraph pitch Everyone at a hackathon gets a personal AI agent that knows their skills, interests, availability, project ideas, and things they'd only tell a friend. The agents find each other on a public board, negotiate over a message bus, reshape project ideas together, and commit to teams, all without anyone, including a central server, seeing everyone's full profile. Information comes out in stages, only to people who have shown real interest, and the privacy rules are enforced by plain code that checks every outgoing message. They never depend on the model choosing to follow instructions.

The problem

Good matching needs private information: what you're good at, when you're free, what you care about, what went wrong last time. The usual fix is a trusted central matcher that collects every full profile and runs an optimizer. That works well, but everyone has to trust one party with everything. The other extreme is a broadcast, where everyone posts everything publicly. It's just as good at matching, and nothing is private.

Agent Match is in between. Each person's data stays with their own agent, agents only learn about each other gradually, and the project measures how much quality that costs and how much privacy it saves (see Evaluation).

Three ideas carry the design

Staged disclosure

Four levels: a public pitch, then interests and availability, then skills and preferences, then names. A level opens only when both sides say "continue".

A deterministic gate

Every model-written word passes checkDisclosure (in gate.ts) before it can be sent. It's plain string matching against the sender's own profile values. No LLM is involved.

Less free text

Where possible, messages have no text at all: accept, continue, withdraw, adopt, commit, and leave. Declines carry one fixed sentence. Profile shares are built by code.

Decentralized decisions

Each agent decides only from its own human's data and what others have shared with it. Teams form by deferred acceptance: owners make offers and people pick, all at the same time.

02

End-to-end flow

The diagram is runSimulation in simulation.ts. Listings are written once. Then each round runs discovery, then conversations (runRound), then commitment (runCommitment), until a round changes nothing. A brainstorm phase follows for anyone left over. Every step emits typed events into one ordered stream, which goes to a JSONL log and the replay UI.

How one tick works (determinism and ordering)
  1. Every agent's inbox is drained in sorted id order. Each message is recorded in the receiver's history, and shares are merged into what it has learned.
  2. All the model calls this tick needs run at once with Promise.all: decisions on proposals and counters, interest checks after shares, and adopt-or-keep on revisions. A hunch call runs first for agents with "never" notes. If a revision arrives in the same tick as a share from the same agent, the interest check waits for the adopt-or-keep answer, so it judges the version that's agreed after that answer (an uncommitted change in round.ts on this branch).
  3. Results are acted on in inbox order, not in the order the calls finish, so what appears on the bus doesn't depend on LLM latency.
  4. Decisions use each agent's state from before this tick's mail, so the message being decided on isn't in the prompt twice. Interest checks use the state after learning the share, because judging the share is the point.
  5. The round ends when no mail is waiting, or after maxTicks (12 by default) so counters can't loop forever.

Agent state is plain immutable data: every update returns a new AgentState, so logged snapshots stay accurate and states survive JSON round trips.

When does the simulation stop?

A round is stable when it had no proposals, no mail left at the tick limit, no commits, and no departures. The normal rounds end when a round is stable or when maxRounds (default 6) is reached. If at least two people are still on no team, up to 2 brainstorm rounds follow. A stopped event records the reason (stable or limit).

The run always ends: a pair that has talked is never approached again, so the untried pairs run out. An agent that picked nobody isn't asked again until the board changes, which also saves model calls.

03

Disclosure levels

The single source of truth is FIELD_LEVELS in disclosure.ts. It uses satisfies Record<ProfileField, DisclosureLevel>, so adding a profile field is a compile error until someone gives it a level. The prompt's disclosure rules, the gate, the share builder, and the leakage metric all read this same table.

LevelFields revealedOpens whenHow it's shared
0 · pitchid, projectIdeasAlways public: board listing, proposalsListing written by the model and gate-checked at L0
1 · fitinterests, availability (hours/week, UTC offset)A proposal or counter is accepted (mutual interest)share message built by code, exactly these fields
2 · skillsskills, preferences (team size range, preferred roles)Both sides sent continue at level 1share built by code
3 · identitynameA commit puts them on the same team; every pair of teammates swaps names, even pairs who never talkedshare built by code during commitment

Notes follow the same scale: a note tagged level 1 enters prompts only once the conversation has reached level 1. Notes tagged never never enter a decision or interest prompt.

Conversations stop at maxLevel = 2. Two agents who have both continued at level 2 are a ready pair. Level 3 is reserved for commitment. Levels only go up, because what was shared can't be unshared.

04

Privacy architecture

The core claimPrivacy must never depend on the model following instructions. The prompt does tell the model the rules, but that only means fewer redrafts. What enforces them is code: schemas, the gate, and messages that have nowhere to put text.

Layer 1: the deterministic gate

checkDisclosure(sender, level, draft) checks two things:

  • Structured shares: every field must be allowed at this level and deep-equal the sender's real profile value. A share can't contain made-up data.
  • Free text (pitch and roles list): it searches for the sender's own values from fields above the level, as whole words and ignoring case. That covers skill names plus synonyms ("server-side" for backend), interests, preferred roles, availability phrasings ("15 hours", "UTC-4"), and the name. A term that's already public through an allowed field doesn't count, so a project idea about physical therapy can be mentioned at level 0 even though "physical therapy" is also an interest.

The roles list is checked too: listing a role your human fills reveals their skill as clearly as saying it. The gate runs inside the model call loop (chatJson's check hook). A violation goes back to the model as feedback and it redrafts, up to 3 attempts. If no allowed draft comes back, the safe fallback is sent instead (a plain decline, or a withdraw).

Layer 3: private reasoning stays private

Every model call returns { rationale, … }, with the rationale first so the model reasons before it decides. Only the decision part becomes a message. The rationale goes to the run log for the agent's own human and is never put on the bus. The prompt says so, and tells the model to "explain yourself fully there", which gives its reasoning somewhere harmless to go.

Layer 4: notes only enter the prompt at their level

The profile is always in the prompt

Its values are short and known, such as "backend" or "UTC-4", so the gate can find them in anything sent. Including the full profile is safe because leaks of it can be detected.

Notes are not

A note like "patients skipped their home exercises" can be paraphrased in endless ways, and no string matching would catch it. So aboutHuman(agent, level) includes only the notes that level allows. A note that isn't in the prompt can't leak.

Layer 5: the hunch pattern for "never" notes

Some things should shape judgment but never be said: "I burned out on a fitness startup last year." The hunch splits seeing from saying:

  1. A separate hunch call (hunch.ts) sees the profile, every note, and what the other side has shared so far. Its output schema allows only a steer from a fixed list (neutral, explore, careful, stop) and a riskArea from another fixed list (retention, scope, market, team, timeline, technical), plus a private rationale.
  2. Code turns that into one fixed sentence (steerText), for example "Your human has private reasons for caution about this, especially around scope." That sentence is the only thing that reaches the decision or interest prompt. The decision call never sees the notes.
  3. The steer is also enforced in code. stop declines or withdraws with no model call at all. careful makes the check hook reject a plain accept, so the agent must counter or decline. If the hunch call fails, it falls back to neutral, which changes nothing.

The channel from the notes to the outside is a few bits wide: four steers times six risk areas. Even a model that wanted to leak the note couldn't fit it through.

Layer 6: offers can't pass on what you learned from others

An owner talking to several people may have agreed on a version of the project with Mara that mentions what Mara shared. Before that version goes to anyone else in an offer, safeToOffer runs checkThirdParty: it searches the pitch for the name, skills (with synonyms), interests, and preferred roles of everyone the owner learned about, except terms the recipient could already see. If anything matches, that person gets no offer.

Layer 7: the bus

Agents never call each other. bus.send(from, message) validates the message against its schema, rejects a message whose from isn't the actual sender, rejects unknown recipients and messages to yourself, and stores separate copies for the inbox and the event log, so neither can change the other. A rejected message is a bug in the sending code, and the bus throws.

Honest limits of this design
  • The free-text gate matches strings. It catches the human's own values and known synonyms. It won't catch a description like "I train neural nets" for ml. That's why free text is limited to pitches and roles, and why notes stay out of the prompt instead of relying on the gate.
  • It protects a person from their own model, not from a malicious peer. The gate runs in the sender's process. An agent whose code was modified could skip it. Defending against adversarial agents (authentication, attestation) is out of scope for this prototype.
  • In the simulation, the bus and logs see everything. The bus is in-process, so the decentralization claim is about who decides, and about no party needing everyone's full profile to compute a match. A real deployment would need encrypted transport between agents.
  • The leakage metric uses the same matching (fieldsMentioned), so it shares the gate's blind spot for paraphrase.

06

Forming teams: deferred acceptance

Ready pairs aren't teams yet. A person may be ready with several owners, and an owner may be ready with more people than it has places. runCommitment settles this without anyone seeing the whole picture, using passes modeled on Gale–Shapley deferred acceptance:

  1. Owners offer. For each project owner, the candidates are people it's ready with, on no team, who haven't declined it or left it before, who fill a role the version still needs (or wrote that version themselves), and whose largest team size fits. If not all of them fit, the owner's model ranks them, and selectOffers trims the ranking so each person fills a different role and the team fits the smallest maxTeamSize among its members. Offers are binding.
  2. Holders pick, all at once. Everyone holding offers chooses one at the same moment, so no offer wins by arriving first. They send commit to their pick and decline to the rest. An agent with its own offers out answers busy without a model call. Unlike a decline, busy leaves them open to the same offer later.
  3. Commits form teams. The member is added to the owner's team (the first member is the owner), and every pair of teammates opens level 3 and swaps names.
  4. Steps 1–3 repeat (up to 5 passes) until a pass has no commits and no declines.
  5. Re-check. In any team that grew, earlier members other than the owner decide whether to stay. Staying is the default and the fallback. Leaving sends a text-free leave to each teammate, frees the place, and increments the leaver's public leftTeams, which appears on their board entry and every proposal they send afterward.
Who owns the project? (agreedVersion and projectOwner)

A version of the project is a pitch plus rolesNeeded, and the roles list names what's needed from people other than its author. So ownership follows authorship. agreedVersion walks the conversation history and returns the last accepted proposal or counter, or the last adopted revision, together with its author. In the example, Mara's counter made her the owner, then Theo's adopted revision made him the owner.

A "Join your project: …" request agrees to the recipient's pitch, so the recipient is the author. In a brainstorm, nobody owns anything until a real idea is agreed. Someone with no project idea can own a project only by writing the idea during a brainstorm.

Each offer carries the version the team will build: the team's version once the team exists, otherwise the version agreed with the first person offered. The public board keeps the original listing.

Who keeps looking after joining a team?

People on a team leave the board and stop discovering. The exception is owners with places left and roles still needed (isOpen). Seekers, people with no project idea, appear only as ids, and only agents with a project can see them.

LLM reliability layer

All agents share one client (createLlmClient), so a single concurrency limit covers the whole run. Each layer handles one kind of failure:

Every fallback leans toward sharing less

CallIf no valid reply after the retriesWhy that default
ListingBuilt-in pitch: first idea + missing core rolesSafe at level 0 by construction
Discovery / brainstorm pickApproach nobody this round (asked again next round)A failed call isn't a choice
DecisionPlain declineNo text, nothing revealed
Interest checkWithdrawContinuing would share more
Revision answerKeep the current versionNothing changes
HunchNeutralAdds no sentence
Owner's rankingId order, trimmed by selectOffersStill a valid set of offers
Which offer to commit toDecline them allA commitment can't be undone
Re-checkStayLeaving breaks a commitment and costs a public mark

Each event records fellBack and gateBlocks, and the simulation report adds them up.

Settings from CLAUDE.md: optional LLM_REASONING_EFFORT is passed as reasoning_effort. Hidden reasoning was about 95% of output tokens in simulations, and minimal cut one decision from 25 s to 2.5 s. -contributor models are about 95% cheaper because the provider trains on their inputs, so they're used only with synthetic profiles.

08

Evaluation

Every method runs on the same generated people (generateProfiles(20, seed) for seeds 1–5) and is scored the same way. The baselines use teams of 3. The agents run the full simulation (up to 6 rounds) on model muse-spark-1.3-contributor with reasoning effort minimal (from results/eval.json).

Methods

  • random: shuffle and deal. The floor.
  • greedy: build teams one at a time, adding whoever raises the score most.
  • local search: greedy, then swap people between teams while any swap helps.
  • broadcast: local search's teams, but everyone sees every full profile.
  • agents: this system.

Metrics

  • Team quality: mean of skill coverage of the 4 core roles (weighted by level), shared interest, and overlap of 9-to-5 workdays across time zones.
  • Placed: share of people on a team.
  • Per-person quality: each person gets their team's score, or 0 if unplaced.
  • Leakage: private fields that reached people outside the sender's final team, out of all possible (a full broadcast ≈ 0.87).
  • Central: needs a trusted party that sees everything.

How to read it

  • The teams that form are good. Agent teams average 0.596, close to local search's 0.600, which uses full information and a central party. Interest (0.727) and time-zone overlap (0.623) are higher than any baseline's.
  • Leakage is a sixth of a broadcast's: 0.149 against 0.874. No trusted party is needed.
  • Placement is the weak spot. Only 72% of people end up on a team, against 100% for the baselines, which force everyone into a team. Because unplaced people count as 0, per-person quality falls to 0.425.
  • The brainstorm phase is the lever being worked on. Adding it raised placement from 67% to 72% and per-person quality from 0.379 to 0.425, with leakage rising from 0.124 to 0.149, since more conversations mean more sharing.

Caveats worth saying out loud. Agent teams are mostly pairs (per-seed results show teams of 2 or 3), while the baselines use teams of 3. Smaller teams find shared interests and overlapping hours more easily but cover fewer roles, which matches the lower skill coverage (0.438 vs 0.556). Profiles are synthetic and the model is a single cheap one, so these are comparisons on one setup, not general claims.

09

Design decisions and trade-offs

Why decentralized, instead of one central matcher?

A central optimizer gives the best teams but needs one party trusted with every full profile, and that party becomes the target for any breach. Here, each agent decides only from its human's data and what was shared with it. The evaluation measures the cost of this choice (placement) as well as the gain (no trusted party, leakage 0.149 instead of 0.874).

Trade-off: more model calls (about 2,000 for the 5-seed, 20-person evaluation), slower convergence, and fewer people placed.

Why staged disclosure?

Most conversations end early. If everything were shared at once, every rejected match would take your whole profile with it. With stages, a pitch that doesn't fit costs nothing beyond what's on the board, and skills are only shown to someone who has already shown interest twice. Leakage counts only what reaches people outside your final team, which is exactly the cost staging reduces.

Why does code build shares instead of the model?

If the model wrote "here are my skills", it could add, omit, exaggerate, or paraphrase. Code takes the exact fields for that level from the real profile, the schema refuses fields from any other level, and the gate checks again that the values match the profile. The model decides whether to go on. It never decides what gets shared.

Why give the gate's violations back to the model instead of just blocking?

A blocked counter that's simply dropped wastes a good idea. The gate runs as chatJson's check, so the model hears exactly what it may not say ("your roles needed list mentions your human's skills…") and redrafts. That feedback goes only to the agent's own model and never to the other side. After 3 attempts, the code falls back to the safe option.

Why deferred acceptance for commitment?

Without it, the result depends on timing: whoever's offer arrives first wins, and an agent might commit before a better offer lands. With offers sent in one pass and every holder choosing at the same time, arrival order doesn't matter. Offers are binding, so owners must commit before they ask, and busy handles an owner who is also holding offers without permanently ruling anyone out. It's an adaptation, not textbook Gale–Shapley: preferences come from model judgments, and teams have several roles and size limits.

Why one ordered event stream, and replay from JSONL for the demo?

The bus and every phase emit typed RunEvents. One stream feeds the log file, the live terminal output, show-run, and the browser UI, so they can't disagree. Replaying a recorded run means a demo costs no credits, has no latency or rate limits, and shows the same thing every time. The engine doesn't depend on the UI, so the UI can change freely.

Logs are gitignored because they contain every agent's private rationale.

Why immutable agent state?

Every update returns a new AgentState, so a logged snapshot can't change after it's written, states survive JSON round trips, and a tick can read "state before this tick's mail" for decisions and "state after" for interest checks without copying bugs.

Why caps on counters, revisions, ticks, rounds, and passes?

Two LLMs can negotiate forever. The hard limits (2 counters and 2 revisions per pair, 12 ticks per round, 6 rounds plus 2 brainstorm rounds, 5 commitment passes) guarantee the run ends. A pair that has talked is never approached again, so the untried pairs run out.

10

Likely interview questions

What stops an agent from leaking data?

Code, not the prompt. Every model-written pitch and roles list goes through a deterministic gate that searches for the human's own above-level values, and the model must redraft until it passes or the code sends a safe default. Shares are built by code and checked against the profile. Most messages have no text field at all, and a decline is one fixed sentence. Rationales are never sent. Free-form notes are kept out of the prompt until their level, and "never" notes only reach a separate call that can output one of a few fixed words.

String matching is easy to get around. Isn't the gate weak?

For arbitrary free text, yes, and the design doesn't pretend otherwise. The gate is reliable for what it targets: short, known profile values and their synonyms. Everything that can't be matched reliably is handled by keeping it out: notes stay out of the prompt, messages have no text, and shares are built by code. If the model never sees a fact, it can't leak it. A semantic checker could be added as an extra layer, but never as the only one.

Why not just use one central matcher?

It needs a party trusted with everyone's full profile. Local search gets 0.600 team quality with 100% placement, but only with that trust. A broadcast gets the same teams with no trusted party, at 0.874 leakage. The agents form teams of almost the same quality (0.596) with no trusted party and 0.149 leakage. The cost is placement, which is what I'm working on.

How do you evaluate it?

Same synthetic people (seeded generator, 20 people, 5 seeds) for every method. Team quality is the mean of role coverage, shared interest, and workday overlap. I also track placement, per-person quality (unplaced counts as 0, so a method can't win by placing only easy people), leakage measured from what each agent actually recorded as revealed to non-teammates, and whether a trusted party is needed. Results go to results/eval.json and a privacy-versus-quality chart.

Why is placement only 72%?

Agents are selective by design: they can decline, withdraw, and run out of untried pairs, and a team needs someone who fills a role the agreed version actually needs. People with no idea of their own, or with uncommon skills, can go unpicked. The brainstorm phase targets this by letting leftovers meet each other with a fixed "let's come up with a project together" pitch, so a team can form around an idea they write together. It moved placement from 67% to 72%.

How do you make LLM output reliable?

Every reply is a JSON object validated against a zod schema. The format instructions are generated from that same schema, so they can't drift apart. A reply that's invalid or breaks a rule is shown back with the problems listed, up to 3 attempts. Transport errors get exponential backoff with jitter and Retry-After. A shared queue caps concurrency. If a call still fails, a safe fallback is used, and it always leans toward sharing less: decline, withdraw, keep, stay.

How do you test code that calls an LLM?

The client accepts a fake fetch and backoff accepts a fake sleep and random source, so tests script exact model replies, including bad JSON and gate violations, and run instantly. The protocol is deterministic for a given set of replies: ids are sorted, actions follow inbox order, and profiles come from a seeded generator. There are 445 Vitest tests. Live scripts (decide, reliability, negotiate, simulate) cover real model behavior, and logs can be replayed.

Isn't the bus a central party?

In the simulation it's an in-process transport. It validates schemas and sender identity and delivers to inboxes, but it doesn't decide anything. It does see messages in transit, which include level shares. A real deployment would put encrypted, authenticated channels between agents so the transport sees only ciphertext. The point is that no party needs everyone's full profile to compute the match.

What breaks at scale?
  • Discovery prompts grow with the board. Every open agent sees every listing, so total prompt tokens grow roughly with n². You'd need retrieval or filtering (embedding search over listings) before the model picks.
  • Calls and cost. The repo's own estimate is about 100–200 calls for 10 agents and 300–450 for 20. The queue and backoff handle rate limits, but at scale throughput is limited by the provider.
  • Trust between agents. The bus checks sender identity in-process. A network needs real authentication, and protection against Sybil agents and agents that ignore the protocol.
  • Convergence. Capped at 3 picks per round and 6 rounds. More people may need more rounds or smarter targeting.
What would you do next?

Some reasonable directions, based on where the results are weakest: raise placement (more from the brainstorm phase, and helping pairs grow into teams of 3), have humans approve or reject the final recommendations (the README's model, and the replay UI already has local approve and pass), move the bus to an encrypted network transport, add retrieval so discovery scales, and evaluate on more seeds, more people, and more than one model.

What was the hardest bug or design problem?

A good one to tell: ownership after reshaping. Once revisions existed, "whose project is this?" wasn't obvious anymore. The fix was to model a version as terms plus an author, with the roles list meaning "needed from people other than the author". agreedVersion derives the current version from history, and projectOwner, offers, and team roles all follow from it. Another: an owner could pass on what it learned from Mara in an offer to Ben, which checkThirdParty now blocks.
